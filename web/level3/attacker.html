Level 3: Attacker view

The code goes to an inbox. Whose inbox is it really?

Simulation against this demo only, using the seeded demo accounts and fake .invalid addresses. Nothing real is involved.

Scenario

You have admin's password (admin123) from the earlier levels. Level 3 emails a code to admin@demo.invalid. Like many people, admin uses the same password for their email account.

  1. Log in with the known password. The site emails a code to admin's mailbox.
  2. Open admin's mailbox. Try the same password on the email account.
  3. Read the code in the mailbox below and enter it.

Mailbox open in your browser

Until you open admin's mailbox (step 2), this stays empty: the code goes somewhere you cannot read.

What this shows

  • The code is only as safe as the mailbox. Anyone who can open the inbox receives the code, and the site cannot tell them from the owner.
  • Ways into a mailbox: a reused or guessed password (shown here), a phishing page for the email provider, malware, or a forwarding rule quietly added after an earlier breach. No SIM swap is needed, so the carrier's controls do not help.
  • Email is the master key. Password resets also go to the mailbox, so controlling it often means controlling every account that uses it.
  • Same weakness as SMS in real time: a fake login page can ask a victim for the code they just received and pass it on within its 10-minute life. This demo does not build such a page.
  • What the code still does well: it is single use, expires, and is capped at 5 guesses. Try wrong codes in step 3 until it locks.

The next level takes the second factor off the network entirely: a code computed on the user's own device that nothing ever sends.
