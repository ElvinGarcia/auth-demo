Level 4: Attacker view

Nothing is sent anywhere. What is left to attack?

Simulation against this demo only, using the seeded demo accounts. Nothing real is involved.

1. What the earlier attacks do here

You know admin's password (admin123). At Levels 2 and 3 you stole the code in transit by swapping a SIM or opening a mailbox. Here the code is computed on admin's own device and never travels, so there is nothing to swap or open.

2. The weak point: the server must keep the secret

To check a code, the server needs the same secret as the user's app, so it stores it in a usable form. Suppose you obtain a copy of the table (an SQL injection, a stolen backup, a misconfigured dashboard):

What this shows

  • What TOTP stops: password-only attacks, credential stuffing, SIM swaps and mailbox takeovers. There is no code in transit to steal, and guessing is capped at 5 tries per login.
  • What it does not stop: a leaked secret (shown above). Encrypting the column helps if only the database leaks, but not if the server's key leaks with it. The same applies to a malware-infected phone, a screenshot of the setup QR code, or a cloud backup of the authenticator app.
  • Real-time phishing still works. A fake login page can ask the victim for the current code and pass it to the real site within its 30 to 90 second life. Nothing in the code says which site is asking. This demo does not build such a page.
  • Codes work once. The server remembers the last accepted time step, so a code captured after the user has used it is worthless. Only a code used first, in time, helps.
  • The setup moment is fragile. Until the first code is confirmed, whoever knows the password can enroll their own device.

The next level changes the design so that a server leak yields nothing useful: the server stores only a public key, and the browser signs a challenge tied to the real site's name.
